# Frontend Handoff — Mora Backend v2

**Backend phase covered by this document: Phase B (router + agents + orchestrator).**
Written so another AI agent (Lovable, Claude Code, or a human frontend dev) can start
building Mora's frontend without re-reading the backend source. Everything here describes
what the backend **actually does today** — nothing aspirational.

See also: [`API_CONTRACT.md`](API_CONTRACT.md) (endpoint-by-endpoint reference) and
[`TYPES.md`](TYPES.md) (TypeScript shapes for every response).

---

## 1. Authentication (Phase A)

**Backend provides:** email+password registration/login, JWT access token (15 min default) +
refresh token (7 days default) with rotation, `GET /users/me`, logout (revokes the refresh
token). No social login. No password reset flow yet.

**Frontend must:**
- Have a Login screen and a Register screen (email, password, display name).
- Store `accessToken` and `refreshToken` (e.g. in memory + a secure storage), attach
  `Authorization: Bearer <accessToken>` to every API call except `/auth/*` and `/health`.
- On a 401, attempt `POST /auth/refresh` once with the stored refresh token; on failure,
  force logout and return to the Login screen.
- Refresh token rotates on every use — **always replace the stored refresh token with the
  one returned by `/auth/refresh`** (the old one becomes invalid immediately).

**Loading / empty / error states:** standard form loading spinner on submit; show the
`message` field from error responses (e.g. "Invalid credentials", "A user with this email
already exists") directly — they're already user-presentable French/English short strings.

**Not available yet:** password reset, email verification, 2FA, social login, "remember me"
beyond the refresh token's own 7-day lifetime.

## 2. The Router (internal, surfaced as metadata)

**Backend provides:** every message sent to `POST /api/v1/messages` is classified by
`MoraRouterService` into a `route` (`direct | personal | professional | hybrid`), a `scope`,
a `space`, an `intent`, a `complexity`, a `securityLevel`, and a `confidence` (0–1). This
classification is deterministic (keyword rules) with an optional LLM fallback for ambiguous
messages — the frontend never calls the router directly, it only receives the result on each
`POST /messages` response and can look up history via `GET /router-decisions`.

**Frontend should:** show the resolved `route`/`space` as a small badge next to Mora's reply
(see §7), not expose "confidence"/"intent" prominently to end users (useful for a debug/dev
panel, not for the main chat UI).

**Not available yet:** the frontend cannot influence routing (no "force personal" toggle) —
that would be a future feature, not built in Phase B.

---

## 3. Direct

**Backend provides:** for simple messages (greetings, small talk, very short/ambiguous
input) Mora replies immediately, **without calling any LLM or agent** — a canned response
generated by the orchestrator itself. Fast, always available even with no LLM configured.

**Frontend should:** render exactly like any other assistant message; no special UI needed.
Optionally show a lightweight "direct" badge in a dev/debug view.

---

## 4. Personal

**Backend provides:** `PersonalAgentService` handles messages routed `personal` (family,
health, personal scheduling, etc.). It only ever sees prior messages of the **same
conversation that are themselves scoped `personal` or `direct`** — never professional
content (enforced server-side, not just a frontend convention).

**Frontend should:**
- Show a distinct visual treatment for personal-scoped messages (e.g. a "Personal" badge
  or a differently colored message bubble), so the user always knows which "hat" Mora is
  wearing for that reply.
- Permissions: any authenticated user can use personal scope; nothing to gate in the UI.

**Data to display:** `route`, `scope`, `space` ("personal") from the `POST /messages`
response.

---

## 5. Professional

**Backend provides:** `ProfessionalAgentService` handles messages routed `professional`,
tagged with one of four **spaces**:

| Space | Trigger examples (keyword-based) |
|---|---|
| `general` | "travail", "client", "facture", "réunion", "projet", "budget"... |
| `logistiga` | message mentions "Logistiga" |
| `piston` | message mentions "Piston" |
| `code` | "code", "bug", "TypeScript", "API", "déploiement", "git"... |

Like Personal, the professional agent only ever sees prior `professional`/`direct` messages
of the same conversation — never personal content.

**Frontend should:**
- Show a **space badge** per message/conversation: "Logistiga", "Piston", "Code",
  "Professionnel" (for `general`). Suggested: a colored chip/tag component, one color per
  space, consistent across the app.
- No permission gating yet — any authenticated user can use any space (a future phase may
  add per-space authorization; not built yet).

**Data to display:** `space` value from every message/router-decision — this is the single
most useful piece of routing metadata for the professional UI.

---

## 6. Hybrid (blocked by default)

**Backend provides:** when a message mixes personal and professional signals, the router
returns `route: "hybrid"`. The orchestrator does **not** call any agent in this case —
`cross_scope` is `false` by default (env `MORA_CROSS_SCOPE_ENABLED`), so it returns a fixed
message asking the user to split their request, and persists that as the assistant reply.

**Frontend must:**
- Treat a `route: "hybrid"` response as a normal assistant message (it already contains the
  "please split your request" text) — no special handling required to make it work, but a
  distinct "Hybrid — blocked" badge is recommended so the user understands *why* they got a
  generic message instead of a real answer.
- Show cross-scope as **disabled** wherever the frontend surfaces settings — e.g. a
  `Paramètres` panel could show "Mode cross-scope : désactivé" as a read-only/disabled
  toggle. There is no endpoint to change it yet (env-only), so don't build a working toggle.

**Not available yet:** real hybrid handling that actually combines personal + professional
context — even if `MORA_CROSS_SCOPE_ENABLED=true` is set, Phase B still returns a "not yet
implemented" message rather than merging scopes (see `MoraOrchestratorService.dispatch`).

---

## 7. Conversations & Messages

**Backend provides:** `POST /api/v1/messages` creates a conversation automatically if no
`conversationId` is given, or continues an existing one (ownership-checked — a user can only
post into their own conversations, 403 otherwise). `GET /conversations` lists the current
user's conversations (newest first). `GET /conversations/:id` returns one conversation with
its full message list, ordered oldest→newest.

**Frontend should build:**
- **Conversation list screen**: title (currently always `null` — see below), last-updated
  time, maybe a preview of the last message (not returned by `GET /conversations` today —
  fetch `GET /conversations/:id` for the full thread).
- **Chat screen**: message bubbles (`role: USER` right-aligned, `ASSISTANT` left-aligned, no
  `SYSTEM` messages are ever created in Phase B so no UI needed for that role), each tagged
  with its `scope`/`space` badge (see §4/§5).
- **Loading state:** while `POST /messages` is in flight, show a typing/thinking indicator
  for Mora's reply.
- **Empty state:** no conversations yet → prompt to start chatting; an open conversation
  with 0 messages cannot happen in practice (a conversation is only created alongside its
  first message).
- **Error state:** `404` (conversation not found), `403` (not yours) — show a generic "this
  conversation is unavailable" and redirect to the conversation list.

**Not available yet:** conversation titles are never set by the backend (`title` is always
`null` today — no auto-titling); no delete/archive/rename conversation endpoint; no
pagination on `GET /conversations` or on a conversation's message list (Phase B has no
volume concerns yet).

---

## 8. Router Decisions (audit/debug view)

**Backend provides:** `GET /api/v1/router-decisions` returns the current user's last 50
routing decisions (newest first), each linked to a `conversationId`/`messageId`.

**Frontend should:** this is **not** a primary end-user screen — build it as an optional
debug/admin panel (e.g. "Routing history") if useful, showing route/scope/space/intent/
confidence per entry. Not essential for a first chat UI.

---

## 9. Audit entries

**Backend provides:** every processed message writes an `AuditEntry` row (action
`message_processed`, plus `crossScopeBlocked` in metadata when relevant). **No API endpoint
exposes audit entries yet** — this is server-side only in Phase B.

**Frontend should:** nothing yet — there is no data to fetch.

---

## 10. LLM configuration & its effect on the UI

**Backend provides:** `LlmService` never crashes the app if no LLM provider is configured
(no `OPENAI_API_KEY` set). Instead, `personal`/`professional` responses come back with a
fixed placeholder message: *"Configuration LLM manquante : aucun provider n'est configuré
(OPENAI_API_KEY absent). Cette réponse est un espace réservé — configurez un provider pour
obtenir une vraie réponse."* `direct` and `hybrid`-blocked responses are unaffected (they
never call the LLM).

**Frontend should:** render this placeholder exactly like a normal assistant message — no
special handling is required for the app to function. Optionally, if useful for an
admin/dev view, the message text itself is a reliable string to detect "LLM not configured"
state (there is no dedicated boolean field in the `POST /messages` response for this today).

**Not available yet:** no endpoint to check/set LLM configuration status directly; no
provider selection UI (single provider, OpenAI-compatible, env-configured only).

---

## 11. Screens the frontend can already build with Phase B

- **Login** / **Register** screens (Phase A auth).
- **Main Chat screen**: send a message, see Mora's reply, with a route/space badge.
- **Conversation list** screen.
- **Personal vs Professional visual distinction** in the chat (badge/color).
- **Space badges**: Logistiga / Piston / Code / Professionnel (general).
- **Router indication**: small badge showing which route Mora used (Direct / Personal /
  Professional / Hybrid).
- **Settings panel** showing cross-scope as **disabled** (read-only in Phase B — no toggle
  endpoint exists).

## 12. Explicitly NOT available yet (do not build UI for these)

Long-term memory, embeddings/semantic search, documents, tools/actions, WhatsApp, email,
calendar integration, voice, avatar, conversation titles/rename/delete, pagination, LLM
provider selection UI, per-space permissions, a working cross-scope toggle, password reset,
audit log UI.

## À maintenir à chaque phase

`FRONTEND_HANDOFF.md`, `API_CONTRACT.md`, and `TYPES.md` are **living documents** — update
all three at the end of every phase (C, D, E, F, G, H) to reflect the real, shipped backend
state, the same way this document was written for Phase B. Never let them describe a
feature that isn't actually implemented yet.

At **Phase H**, these three documents (accumulated across all phases) will be used to
generate `docs/frontend/LOVABLE_MASTER_PROMPT.md` — a single consolidated prompt handing the
full, final backend contract to Lovable (or an equivalent frontend-generation agent) to build
the complete Mora frontend in one pass.
